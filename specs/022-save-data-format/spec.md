# 022 — 세이브 · 데이터 포맷 · 모드 스키마

상태: 초안
브랜치: feat/022-save-data-format

## 배경
커리어 게임에서 세이브가 깨지면 수십 시간이 날아간다. 버그가 가장 치명적인 곳이다. 세계·선수 DB는 수만 명 단위라 질의가 필요하고(SQLite), 세이브는 그 DB의 스냅샷 + 메타 정보다. 또 "데이터는 공개 포맷으로 저장해 에디터와 모드로 연다"는 것이 아키텍처 원칙이다. 커뮤니티가 로스터 파일을 만들어 공유할 수 있어야 하고, 우리 시즌 패치도 같은 포맷을 쓴다(00 문서 § 2). 이 스펙은 세이브 파일 구조, 스키마 버전과 마이그레이션, 원자적 저장·복구, 공개 JSON 로스터·모드 포맷을 정한다. 가져오기 UI는 049, 실명 데이터 정책은 결정 대기다.

## 범위
- 포함:
  - 세이브 슬롯 구조: 세계·커리어 DB 파일 + JSON 메타 파일 (+ 썸네일)
  - 저장 대상 목록과 소유 스펙 (어떤 상태를 저장하는지, 각 스펙이 필드를 정의)
  - 스키마 버전, 마이그레이션 체인, 이전 버전 세이브 읽기
  - 원자적 저장 (중간에 꺼져도 이전 세이브가 살아 있음), 손상 감지, 자동 백업
  - 자동 저장 시점 규칙 (언제 저장하는지 — 호출은 024)
  - 경기 기록 저장: 결과·스탯 + 다시보기용 (시드, 입력 로그, 시뮬 버전, 체크포인트)
  - 공개 JSON 포맷: 로스터(국가·리그·클럽·선수·감독), 시나리오(013/014 스키마 참조), 일정(021 형식 참조), 이름 데이터
  - 포맷 검증 (스키마 검사, 참조 무결성, 범위 검사) 과 오류 보고
  - 기본 DB 생성 (020 월드 생성 결과 → DB)
- 제외:
  - 인게임 에디터·가져오기 화면 (049)
  - 로스터 업데이트 서버 운영·배포 (운영 범위)
  - 실명·변형 이름 데이터 (결정 대기 — 00 문서)
  - 클라우드 세이브 동기화 [미정: 이후]
  - 각 도메인 필드의 의미 (해당 스펙이 정의 — 이 스펙은 저장 규칙만)

## 사용자 시나리오
1. 시즌 중간에 게임을 끄고 다음 날 켜면 "이어하기"에서 마지막 주 그대로 시작한다. 슬롯 목록에 선수 이름·나이·클럽·날짜·플레이 시간·썸네일이 보인다.
2. 저장 도중 노트북 배터리가 꺼져도, 다시 켜면 직전 세이브가 멀쩡하다.
3. 게임 업데이트 후에도 예전 세이브를 열 수 있다. 처음 열 때 "세이브를 새 버전으로 바꿨어요"라고 알려주고, 원본은 백업으로 남는다.
4. 커뮤니티가 만든 로스터 JSON 파일을 가져오면(049), 형식이 틀린 부분은 줄 번호와 이유가 보인다.
5. 지난 경기 다시보기를 누르면 저장된 시드·입력 로그로 같은 경기가 다시 재생된다(시뮬 버전이 같을 때).

## 요구사항

### 세이브 구조
- FR-01: 세이브 슬롯 = 폴더 하나: 세계·커리어 DB 파일 1개, 메타 JSON 1개, 썸네일 이미지 1개 [제안], 백업 폴더. (기획서 6: SQLite 파일 + JSON 메타)
- FR-02: 메타 JSON: 세이브 형식 버전, 스키마 버전, 게임 버전, 시뮬 버전, 생성·마지막 저장 시각(실제 시각 — 표시용, 게임 로직에 쓰지 않음), 게임 내 날짜, 선수 요약(이름, 나이, 클럽, 포지션), 플레이 시간, 세계 시드, 사용 모드 목록(id·버전·해시), DB 파일 해시.
- FR-03: 슬롯 목록 화면은 **메타 JSON만 읽어** 표시한다 (DB를 열지 않음 — 빠른 목록).
- FR-04: 슬롯 수 [제안] 수동 10개 + 자동 저장 3개(순환).
- FR-05: 세이브 위치는 OS 사용자 데이터 폴더. 검증 실행(000)은 전용 폴더를 쓴다.

### 저장 대상
- FR-10: 저장 대상: 세계(국가·리그·클럽·선수·감독·시설·이적 예산 — 020), 일정·결과(021), 선수 생성 입력·시드·모델 버전(023), 커리어 상태·사기(024), 감독 신뢰·FormEMA·주장(025), 성장 이력(026), 건강(027), 계약·수입 기록·협상 진행(028), 이적·가치 기록·협상 진행(029), 스토리렛 상태·쿨다운·지연 큐·인용 시드(030), 라이프 장부·자산(032), 관계·가족·자녀 기록(033), 평판·팔로워·스폰서·피드(034), 대표팀 기록·대회 진행(035), 은퇴 잠금·커리어 스냅샷(036), 경기 기록(FR-40), RNG 상태(001 — 커리어 진행용 시드 스트림 위치), 설정 중 세이브에 묶이는 것(난이도 등).
- FR-13: **명예의 전당(036) 파일**: 세이브 슬롯과 별도의 사용자 데이터 파일 1개. 세이브를 지워도 남는다. 자체 형식 버전·마이그레이션 규칙은 FR-20~24와 같고, 원자적 쓰기(FR-30)를 쓴다. 항목 단위 손상 격리 (손상 항목만 건너뜀, 036 FR-42).
- FR-11: 각 스펙은 자기 상태의 저장 필드를 정의하고, 이 스펙의 규칙(버전·마이그레이션·검증)을 따른다. 저장 대상이 아닌 상태(캐시, 프레젠테이션 상태)는 로드 후 다시 계산할 수 있어야 한다.
- FR-12: **저장 → 로드 왕복 불변식**: 저장 직후 로드한 게임 상태는 저장 전 상태와 같다 (도메인 상태 해시 일치). 로드 후 같은 입력으로 진행하면 저장하지 않고 진행한 것과 같은 결과가 나온다 (RNG 상태 포함).

### 스키마 버전 · 마이그레이션
- FR-20: 스키마 버전은 정수, 변경마다 +1 (40-data.md). 스키마 변경 PR에는 마이그레이션 단계가 반드시 포함된다.
- FR-21: 마이그레이션은 v→v+1 단계의 체인. 오래된 세이브는 단계들을 차례로 적용한다. 각 단계는 결정론적이고 멱등이 아니어도 되지만, 한 번만 적용되도록 버전으로 보호한다.
- FR-22: 마이그레이션 전에 원본을 백업 폴더에 복사한다. 마이그레이션이 실패하면 원본을 건드리지 않고 실패 이유를 보여준다.
- FR-23: 지원 범위: 출시 후 모든 이전 스키마 버전 [제안] (최소한 직전 [제안] 2개 메이저 버전). 더 새 버전의 세이브(다운그레이드)는 열지 않고 "새 버전에서 만든 세이브" 안내.
- FR-24: 각 스키마 버전마다 테스트용 세이브 픽스처를 저장소에 남긴다 (마이그레이션 회귀 테스트용).

### 원자적 저장 · 손상 · 백업
- FR-30: 저장은 원자적이다: 임시 파일에 쓰고 무결성 확인 후 교체. 교체 직전·직후 어느 시점에 꺼져도 "이전 세이브" 또는 "새 세이브" 중 하나가 온전히 남는다.
- FR-31: DB와 메타는 한 세트로 교체한다 (메타의 DB 해시로 짝 확인). 짝이 안 맞으면 손상으로 본다.
- FR-32: 로드 시 무결성 검사: DB 자체 무결성 검사, 메타 해시 대조, 필수 테이블·버전 확인. 실패 시 백업에서 복구를 제안한다.
- FR-33: 자동 백업: 저장할 때마다 직전 세이브를 백업으로 [제안] 3세대 보관.
- FR-34: 디스크 공간 부족·쓰기 권한 없음: 저장 실패를 명확히 알리고, 기존 세이브는 그대로 둔다. 게임은 계속 진행 가능.

### 자동 저장
- FR-35: 자동 저장 시점 [제안]: 주 시작, **경기 시작 직전**(FR-36 복구 지점 — 확정 (2026-11-02 사용자 결정)), 경기 후(결과 반영 직후), 이적·계약 확정 직후, 시즌 전환 직후. 호출은 024.
- FR-36: **경기 중 저장 없음** (확정 (2026-11-02 사용자 결정)). 저장은 경기 전·후만 한다. 하이라이트·키 모먼트 진행 중 앱이 꺼지면 다음 실행 시 경기 시작 직전 자동 저장 지점(FR-35)으로 복구한다. 같은 시드라 키 모먼트 선택 전까지의 결과는 똑같이 재현되고, 키 모먼트는 다시 고른다 (019). 그래서 시나리오 실행 상태(013)·재시뮬 상태(019)는 세이브 대상이 아니다.
- FR-37: 저장 중에도 UI가 멈추지 않는다 (프레임 예산 안 — 성능 예산 표).

### 경기 기록
- FR-40: 경기마다 저장: 결과(스코어, 득점자, 카드), 선수 스탯·평점(015), 내 선수 키 모먼트 기록(019), 하이라이트 장면 목록(선택 — 재계산 가능, 018).
- FR-41: 다시보기용: 시드, 라인업, 전술, 입력 로그(키 모먼트 선택), 시뮬 버전 (07 § 2.3 방식 B). 체크포인트 형식·크기(≤ 16 KB/개)와 보관 모드(전체 / 키 모먼트만 / 없음)는 **006 FR-55가 소유**하고, 이 스펙은 그 바이트를 그대로 저장한다. 보관 모드 "전체"는 [제안] 내 선수 경기 최근 5경기만 — 용량 때문.
- FR-42: 시뮬 버전이 다르면 다시보기를 재시뮬하지 않고 "이 버전에서는 다시보기 불가 — 결과 요약만" 상태로 둔다 (결과는 저장값이 기준).
- FR-43: 비관전 경기(016)는 결과와 요약 스탯만 저장.

### 공개 JSON 포맷 (로스터 · 모드)
- FR-50: 공개 포맷은 문서화된 JSON (LF, 2칸 들여쓰기, camelCase 키 — 40-data.md). 형식 버전 필드 필수. 기본 DB의 시즌 패치와 커뮤니티 파일이 **같은 포맷**이다 (00 문서 § 2).
- FR-51: 로스터 포맷: 국가, 리그(디비전·승강 규칙), 대회, 클럽(이름·도시·색·명성·재정·경기장), 선수(이름, 생년월일, 국적, 키·체중, 주발, 포지션, 능력치, 성향, 버릇, 성격, 숨김값, 소속·계약 요약), 감독. 필드 정의는 002·003·020·028이 제공, 이 스펙은 직렬화 규칙과 버전만.
- FR-52: 엔티티 참조는 파일 안 문자열 id로 한다 (`"clubId": "club-..."`). 숫자 DB 키를 노출하지 않는다. 가져오기 시 id 충돌 규칙: 같은 id = 덮어쓰기, 새 id = 추가 [제안].
- FR-53: 부분 패치: 파일이 일부 엔티티·일부 필드만 담을 수 있다 (예: 선수 능력치만). 지정 안 한 필드는 유지.
- FR-54: 이미지(엠블럼 등)는 JSON 안에 넣지 않고 같은 패키지 폴더의 파일 경로로 참조 [제안]. 허용 형식·크기 상한 [미정].
- FR-55: 시나리오·일정 파일은 각각 013/014·021의 스키마를 따르고, 같은 버전·검증 규칙을 쓴다.
- FR-56: 모드 패키지 메타: id, 이름, 버전, 대상 게임 데이터 버전, 포함 파일 목록, 작성자 표기(자유 텍스트). 세이브 메타에 사용 모드가 기록된다 (FR-02).

### 검증
- FR-60: 가져오기·로드 전 검증 3단계: ① 스키마(필드 존재·타입) ② 범위(능력치 1~20, 성향 0~100, 날짜 유효, 키 범위 등 — 각 스펙의 값 범위) ③ 참조 무결성(없는 클럽 id 참조, 순환 참조, 중복 id).
- FR-61: 오류 보고: 파일 경로, 줄·열, JSON 경로, 규칙, 받은 값, 기대 값. 오류가 있으면 부분 적용하지 않는다 (전부 적용 또는 전부 거부) [제안].
- FR-62: 경고(적용은 됨): 알 수 없는 필드(무시), 권장 범위 밖 값. 경고 목록도 보고.
- FR-63: 텍스트 인코딩 UTF-8만 허용. BOM은 허용하되 무시.
- FR-64: 파일 크기 상한 [제안] 패키지당 200 MB, JSON 파일당 50 MB. 깊이·배열 길이 상한으로 악성·손상 파일에 대비.

## 경계 · 예외 상황
- 저장 중 강제 종료(각 단계 직전·직후): FR-30 보장.
- 메타만 있고 DB 없음 / DB만 있고 메타 없음 / 해시 불일치: 손상 처리, 백업 복구 제안.
- 빈 세이브 폴더, 0바이트 DB, 잘린 DB.
- 같은 슬롯에 연속 저장 요청(자동 저장과 수동 저장이 겹침): 순서대로 처리, 마지막 요청이 최종본. 동시에 두 쓰기가 일어나지 않는다.
- 저장 경로에 한글·공백·이모지가 들어간 사용자 이름.
- 디스크 가득 참 (임시 파일 쓰기 중 실패): 기존 세이브 보존, 임시 파일 정리.
- 시스템 시각이 과거로 돌아감: 메타의 실제 시각은 표시용이라 로직에 영향 없음. 슬롯 정렬은 저장 일련번호 기준 [제안].
- 매우 오래된 세이브(마이그레이션 단계 다수): 체인 전체 적용 시간도 성능 예산 안.
- 마이그레이션 중 실패한 단계: 원본 그대로, 어느 단계에서 실패했는지 보고.
- 모드가 사라진 세이브: 세이브 메타에 모드가 있는데 설치돼 있지 않음 → [제안] 경고 후 열기 허용(모드 데이터는 이미 DB에 반영돼 있음).
- JSON: 중복 키, 숫자 범위 초과(1e309), NaN/Infinity 문자열, 아주 긴 문자열(이름 10만 자), 깊은 중첩, 잘못된 UTF-8 → 모두 명확한 오류, 예외로 게임이 죽지 않음.
- 능력치 범위 밖(0, 21, 음수, 소수): 오류.
- 선수 생년월일이 미래이거나 게임 날짜 기준 만 15세 미만 (선수 최소 나이 15 — 확정 (2026-11-02 사용자 결정). 023 FR-03 시작 나이 하한, 유스 생성 020 FR-48과 같은 값): 오류.
- 같은 이름의 선수 여러 명: 허용 (id로 구분).

## 비기능 요구사항
- 결정론: 같은 상태 → 같은 DB 내용(행 순서 무관하게 정렬된 해시 기준으로 동일) → 같은 상태 해시. 저장·로드는 RNG 상태를 보존한다.
- 세이브 호환: 이 스펙 자체가 호환 규칙. 스키마 변경 시 마이그레이션·픽스처·테스트 3종 세트 필수.
- 보안: 가져온 파일은 데이터로만 다룬다. 실행 가능한 내용(스크립트)을 받지 않는다.
- 플랫폼: macOS·Windows 경로 규칙 모두. 파일 이름 대소문자 차이에 의존하지 않는다.
- 저장 형식에 실존 인물 데이터를 기본 포함하지 않는다 (01-legal 규칙).

## 수용 기준
- AC-01 [결정론]: 고정 시드로 3시즌 진행한 상태를 저장 → 로드하면 도메인 상태 해시가 같다. 로드 후 10주 진행한 결과와, 저장 없이 10주 진행한 결과의 해시가 같다.
- AC-02 [로직]: 저장 과정을 각 단계(임시 쓰기 중, 무결성 확인 후, 교체 직전, 교체 직후)에서 강제로 끊는 결함 주입 테스트 4종 모두에서 이전 세이브 또는 새 세이브 중 하나가 온전히 열린다.
- AC-03 [로직]: 메타만 있음, DB만 있음, 해시 불일치, 0바이트 DB, 잘린 DB 픽스처를 열면 각각 손상으로 판정되고 백업 복구 경로가 제시되며 예외로 중단되지 않는다.
- AC-04 [로직]: 스키마 버전별 픽스처 세이브(존재하는 모든 버전)가 최신 버전으로 마이그레이션되고 로드 후 상태 검증을 통과한다. 원본이 백업에 남는다.
- AC-05 [로직]: 마이그레이션 단계 하나를 일부러 실패시키면 원본은 그대로이고, 실패 단계 번호가 보고된다.
- AC-06 [로직]: 더 새 스키마 버전 세이브를 열면 열지 않고 안내 상태를 반환한다.
- AC-07 [로직]: 디스크 가득 참·쓰기 권한 없음 결함 주입에서 기존 세이브가 보존되고 임시 파일이 남지 않는다.
- AC-08 [로직]: 자동 저장과 수동 저장을 동시에 요청하면 두 쓰기가 겹치지 않고, 최종본이 마지막 요청 상태다.
- AC-09 [로직]: 유효한 로스터 JSON 픽스처를 가져오면 모든 엔티티가 반영되고, 부분 패치 픽스처는 지정 필드만 바뀐다.
- AC-10 [로직]: 오류 픽스처 세트(타입 오류, 범위 밖 능력치, 없는 clubId 참조, 중복 id, 중복 키, NaN, 잘못된 UTF-8, 50 MB 초과, 깊이 초과)마다 오류가 파일·줄·JSON 경로·규칙과 함께 보고되고, 아무것도 적용되지 않는다.
- AC-11 [로직]: 기본 DB 시즌 패치 파일과 커뮤니티 로스터 파일이 같은 검증기로 통과한다 (포맷 동일성).
- AC-12 [로직]: 저장 경로에 한글·공백·이모지가 포함돼도 저장·로드가 된다.
- AC-13 [로직]: 시뮬 버전이 같은 경기 다시보기는 저장된 시드·입력 로그로 재시뮬한 결과 해시가 저장된 결과와 같고, 시뮬 버전이 다르면 재시뮬하지 않고 "다시보기 불가" 상태가 된다.
- AC-14 [성능]: 저장·로드·목록·마이그레이션·검증 시간과 세이브 크기가 성능 예산 표 안에 든다.
- AC-15 [E2E]: `e2e/022-save-slots` — 고정 세이브 3개가 있는 상태에서 이어하기·슬롯 목록 화면(선수 요약, 게임 날짜, 플레이 시간, 썸네일, 손상 슬롯 표시 1개 포함)이 기준 이미지와 일치하고 en에서 긴 이름이 잘리지 않는다. 프로필: 전체.
- AC-16 [E2E]: `e2e/022-save-roundtrip` — 주간 화면에서 저장 → 메인 메뉴 → 로드 후 주간 화면 스크린샷이 저장 전 스크린샷과 같다(카운트업 등 마스크 제외). 저장 중 프레임이 예산을 지킨다. 프로필: smoke.
- AC-17 [E2E]: `e2e/022-migration-notice` — 이전 스키마 픽스처 세이브를 열면 "새 버전으로 바꿨어요" 안내가 뜬다. 프로필: smoke.
- AC-18 [로직]: 명예의 전당 파일이 세이브 슬롯 삭제 후에도 남고, 쓰기 도중 강제 종료해도 이전 내용이 온전하며, 항목 1개를 손상시키면 그 항목만 빠지고 나머지는 읽힌다.
- AC-19 [로직]: 하이라이트 재생 중 프로세스를 강제 종료한 픽스처에서 재실행하면 경기 시작 직전 저장 지점이 로드되고, 같은 입력으로 다시 진행한 경기 결과 해시가 종료 전 진행분(키 모먼트 이전 구간)과 같다. 경기 중에는 저장 API 호출이 거부된다(호출 0회 성공).

- [미정] 실명·변형 이름 데이터 정책(00 문서) — 공개 포맷은 그 결정과 무관하게 동작해야 하지만, 기본 배포 데이터 내용은 결정에 따른다.
- 정리됨: 경기 중 저장 없음, 경기 시작 직전 복구 (FR-36, 확정 (2026-11-02 사용자 결정)).

- [미정] 체크포인트 보관 정책(최근 몇 경기) — 용량 대 다시보기 기능.
