# 000 — 검증 하네스 · 디바이스팜

상태: 완료
브랜치: feat/000-verification-harness
기획 출처: docs/index.html § 기획서 5.5.1(그래픽 목표·성능 예산), § 7(로드맵 M0 완료 기준), § 8(리스크: 회사 업무와 병행) / § 아키텍처 2(asmdef: Tests는 Unity 없이 대량 시뮬)

## 배경
1인 개발이고 회사 업무와 병행한다. 개발 PC 앞에 없을 때도 "정말 동작하는지"를 눈으로 확인할 수 있어야 한다. 그래서 모든 스펙의 완료를 **말이 아니라 증거**로 판정한다. 로직은 테스트 리포트 스크린샷으로, 화면은 여러 기기 조건에서 찍은 스크린샷으로, 성능은 기기별 측정값으로 남긴다. 여러 기기 프로필에 같은 시나리오를 돌리고 결과를 한 화면 격자로 모아 보는 **디바이스팜** 방식이다. 이 스펙은 다른 모든 스펙의 `[로직]` `[E2E]` `[성능]` `[결정론]` 검증이 기대는 기반이다.

## 범위
- 포함:
  - 로직 테스트 실행 → 결과 리포트 렌더링 → 스크린샷
  - 기기 프로필 정의와 프로필 매트릭스 실행 (해상도·화면비·DPI 배율·품질 프리셋·렌더 스케일·테마·언어·배터리 절약 모드·목표 fps)
  - E2E 시나리오 정의 형식과 실행기 (UI 조작, 대기, 단언, 캡처)
  - 스크린샷 기준 이미지 비교 (픽셀 차이, 마스크 영역)
  - 프레임 시간·GC·드로우콜·삼각형·메모리 측정과 예산 판정, 이전 측정 대비 회귀 판정
  - 결정론 검증 (같은 시드 2회 → 해시 비교)
  - 콘솔 에러·경고·예외·크래시·타임아웃 감지
  - 스펙별 증거 리포트(HTML) 생성과 아티팩트 발행
- 제외:
  - 실제 원격 물리 기기 연결 (이후 확장. 프로필 형식은 원격 기기를 붙일 수 있게 열어 둔다)
  - 클라우드 CI 서버 구축 (로컬 맥에서 한 명령으로 도는 것이 목표)
  - 모바일 빌드 실행 (모바일 화면비는 데스크톱 창 크기로 흉내 낸다)

## 사용자 시나리오
1. 개발자가 태스크를 끝내고 `/verify 012`를 실행하면, 몇 분 뒤 리포트 링크를 받는다. 휴대폰으로 열면 로직 테스트 결과 스크린샷, 프로필별 화면 격자, 성능 표가 보인다.
2. 리포트에서 한 칸이 빨갛다. 누르면 기준 이미지·현재 이미지·차이 오버레이를 나란히 보고, 어떤 단계·프로필에서 깨졌는지 바로 안다.
3. 성능 표에서 `low-igpu-1080p`의 p95 프레임 시간이 예산을 넘어 빨갛다. 이전 측정 대비 몇 % 늘었는지 보인다.
4. 새 화면이라 기준 이미지가 없으면 "기준 후보"로 표시된다. 개발자가 승인하면 그때부터 기준이 된다.

## 요구사항

### 로직 증거
- FR-01: EditMode 테스트를 배치모드로 돌리고(스펙 번호·클래스·카테고리로 필터), 결과를 HTML 리포트로 렌더링해 PNG 스크린샷으로 저장한다. 리포트에는 테스트 이름, 결과, 소요 시간, 실패 메시지·스택, 실행 일시, 커밋 해시, 브랜치, Unity 버전이 보인다.
- FR-02: 실패 테스트가 있으면 리포트 맨 위에 실패 목록이 먼저 보인다. 실패 0이어야 로직 검증 통과.
- FR-03: 컴파일 에러로 테스트가 돌지 않으면 그것도 실패로 리포트에 남긴다 (에러 줄 포함).

### 기기 프로필
- FR-10: 프로필은 데이터 파일 하나에 정의한다. 필드: id, 설명, 창 해상도, DPI 배율(UI 스케일), 화면비, 품질 프리셋(Low/Medium/High), 렌더 스케일, 목표 fps, 테마(light/dark), 언어(ko/en), 배터리 절약 모드, 기준 기기 여부(성능 판정 대상인지), 등급(smoke/full).
- FR-11: 기본 프로필 세트 (화면비·UI 밀도·성능 조건을 고르게 덮는다):

  | id | 해상도 | 배율 | 품질 / 렌더 스케일 | 비고 | 등급 |
  |---|---|---|---|---|---|
  | `low-igpu-1080p` | 1920×1080 | 1.0 | Low / 0.67 | 최소 사양 대표 (내장 GPU) | smoke |
  | `mac-m1-1600p` | 2560×1600 (16:10) | 2.0 | Medium / 0.75 | 개발 기기 | smoke |
  | `compact-1366` | 1366×768 | 1.0 | Low / 0.75 | 작은 노트북, 세로 공간 부족 | smoke |
  | `handheld-800p` | 1280×800 | 1.0 | Low / 0.75 | 휴대형 PC 화면 | full |
  | `ultrawide-1080` | 2560×1080 (21:9) | 1.0 | Medium / 1.0 | 넓은 화면 레이아웃 | full |
  | `desktop-1440p` | 2560×1440 | 1.0 | High / 1.0 | 상위 설정 | full |
  | `uhd-4k-200` | 3840×2160 | 2.0 | Medium / 0.5 | 고DPI UI 배율 | full |
  | `tablet-4x3` | 2048×1536 (4:3) | 2.0 | Low / 0.75 | 이후 모바일 대비 | full |
  | `phone-portrait` | 1170×2532 | 3.0 | Low / 0.67 | 이후 모바일 대비, 세로 | full |
  | `phone-landscape` | 2532×1170 | 3.0 | Low / 0.67 | 하이라이트 가로 재생 | full |

- FR-12: 테마(light/dark)와 언어(ko/en)는 프로필에 곱해지는 축이다. smoke 등급은 `ko+light` 1개, full 등급은 `ko/en × light/dark` 4개 조합을 돈다. 배터리 절약 모드는 지정한 시나리오에서만 켠다.
- FR-13: 각 스펙의 E2E 시나리오는 대상 프로필을 `전체 | smoke | 목록`으로 지정한다.

### E2E 시나리오와 실행
- FR-20: E2E 시나리오는 데이터 파일로 쓴다. 단계 종류: 화면 이동, UI 요소 누르기(요소 이름으로), 텍스트 입력, 조건 대기(요소 등장, 시뮬 시각 도달, 하이라이트 장면 n 시작), 단언(요소 보임·텍스트·숫자 범위·겹침 없음·화면 밖으로 잘림 없음), 캡처(이름), 성능 구간 시작·끝, 결정론 체크포인트.
- FR-21: 게임 상태는 시나리오 시작 시 **고정 세이브 픽스처 + 고정 시드**에서 출발한다. 같은 시나리오는 언제 돌려도 같은 화면이 나와야 한다 (시계·랜덤·네트워크 의존 제거).
- FR-22: 실행기는 프로필마다 독립 프로세스로 플레이어를 띄우고, 창 크기·품질·렌더 스케일·테마·언어를 실행 인자로 적용한다. 한 프로필이 크래시해도 다른 프로필은 계속 돈다.
- FR-23: 캡처 시점에는 애니메이션·카운트업·트랜지션이 끝났는지(또는 고정 시점인지) 보장한다. 깜빡이는 커서, 시간 표시 등은 마스크 영역으로 비교에서 뺀다.
- FR-24: 단계별 타임아웃 (기본 10초, 시나리오가 늘릴 수 있음). 타임아웃·예외·크래시는 그 단계 스크린샷과 로그를 남기고 실패 처리.
- FR-25: 하이라이트·3D 시나리오는 지정 시뮬 시각 또는 장면 번호에서 프레임을 고정해 캡처한다 (재생 속도 1x/1.5x/2x/3x, 0.5x 리플레이 포함).
- FR-26: 단언 `겹침 없음`·`잘림 없음`은 UI 요소 사각형을 검사해 텍스트가 부모 밖으로 넘치거나 서로 겹치는 경우를 잡는다 (en 같은 긴 문자열에서 깨지는 레이아웃 감지).

### 스크린샷 비교
- FR-30: 기준 이미지는 `(시나리오, 단계, 프로필, 테마, 언어)`마다 하나. 저장소에 LFS로 둔다.
- FR-31: 비교: 픽셀 채널 차이가 임계값(기본 8/255)을 넘는 픽셀 비율이 기본 0.1%를 넘으면 실패. 시나리오가 단계별로 임계값·마스크를 바꿀 수 있다. 3D 장면은 기본 비율 0.5%.
- FR-32: 차이 이미지(바뀐 픽셀 강조)를 만든다.
- FR-33: 기준 이미지 갱신은 명시적 승인 명령으로만. 자동 갱신 금지.
- FR-34: 비교와 별도로 **빈 화면·단색 화면·검은 화면**은 기준과 무관하게 실패 (렌더 실패 감지).

### 성능
- FR-40: E2E의 성능 구간마다 프로필별로 프레임 시간(평균·p50·p95·p99·최대), 메인 스레드 시간, GC 할당(프레임당, 구간 합계), 드로우콜, 화면 내 삼각형, 텍스처 메모리, 총 메모리를 기록한다. 측정 전 워밍업 구간은 버린다.
- FR-41: 순수 C# 코어 성능(경기 1개 시뮬 시간, 틱당 할당, 1,000경기 처리량)은 Performance 테스트로 측정한다.
- FR-42: 각 스펙의 성능 예산 표와 비교해 통과/실패. 예산이 없는 항목은 기록만 한다.
- FR-43: 이전 통과 측정(같은 프로필·같은 시나리오)과 비교해 +10% 이상 나빠지면 **회귀 실패**. 기준 측정 갱신도 승인 명령으로만.
- FR-44: 측정에는 기기 정보(CPU, GPU, OS, 전원 연결 여부)를 같이 남긴다. 성능 판정은 프로필의 `기준 기기 여부`가 참인 측정만 쓴다 (흉내 낸 프로필은 상대 비교용).

### 결정론
- FR-50: 같은 시드·같은 입력으로 시뮬을 2회 돌려 시뮬 이벤트 로그 해시가 같은지 확인한다. 체크포인트별 해시도 비교해 어느 시점부터 갈라졌는지 보고한다.
- FR-51: E2E 결정론 체크포인트에서도 같은 해시를 기록해, 같은 시나리오의 프로필 간 시뮬 결과가 같은지 확인한다 (화면 해상도가 시뮬에 영향을 주면 안 된다).

### 로그와 실패 감지
- FR-60: 플레이어·에디터 로그에서 에러·경고·예외·어서션을 모은다. 1개라도 있으면 실패. 알려진 무시 목록은 사유와 함께 파일로 관리하고 리포트에 보인다.
- FR-61: 크래시, 행(무응답 30초), 비정상 종료 코드는 실패.

### 리포트
- FR-70: 스펙별 `specs/NNN-*/evidence/`에 결과를 모은다: 로직 스크린샷, 프로필별 캡처, 차이 이미지, 성능 JSON, 로그 요약, `report.html`.
- FR-71: `report.html`: 맨 위 요약(통과/실패, AC별 상태), AC ↔ 증거 연결표, 로직 리포트 스크린샷, **화면 격자**(행=단계, 열=프로필, 칸=썸네일+상태 색, 누르면 기준·현재·차이 3장 비교), 성능 표(예산·이전 대비), 결정론 결과, 로그 요약. 휴대폰 폭(400px)에서도 읽힌다.
- FR-72: 리포트는 아티팩트로 발행하고 링크를 남긴다. 같은 스펙은 같은 링크로 갱신한다. 이미지는 리포트용으로 압축해 아티팩트 용량 한도를 넘지 않게 한다 (원본은 로컬 보관).
- FR-73: 리포트 상단에 커밋 해시·브랜치·실행 일시·실행 시간·프로필 목록을 표시해, 어떤 코드의 증거인지 분명히 한다. 작업 트리에 커밋 안 된 변경이 있으면 경고 표시.
- FR-74: 전체 스펙 대시보드: 스펙별 마지막 검증 결과를 한 페이지에 모은다 (선택 실행).

### 사용성
- FR-80: 한 명령으로 실행: 로직만 / smoke / full / 특정 프로필. 진행 상황을 단계별로 출력한다.
- FR-81: 실행기 자체의 실패(도구 없음, 빌드 실패, 디스크 부족)는 "검증 실패"와 구분해 표시한다.

### 경계 · 예외 상황
- 프로필 해상도가 실제 모니터보다 크면 창이 잘리거나 OS가 줄인다 → 오프스크린 렌더 타깃으로 캡처하고, 캡처 해상도 ≠ 프로필 해상도면 실패.
- 디스플레이 배율(레티나 2x)이 캡처 크기를 두 배로 만드는 경우 → 프로필 해상도 기준으로 판정.
- 기준 이미지와 캡처 해상도가 다르면 비교하지 않고 실패 (리사이즈 비교 금지).
- 폰트 미로딩·첫 프레임 셰이더 컴파일로 첫 캡처만 다른 경우 → 캡처 전 워밍업 프레임, 2회 연속 동일 프레임 확인.
- 노트북 절전·화면 잠금·전원 분리로 성능이 흔들리는 경우 → 측정에 전원 상태를 기록하고, 배터리 상태 측정은 성능 판정에서 제외.
- 동시에 두 검증 실행 → 잠금 파일로 하나만 허용.
- Unity 에디터가 프로젝트를 열고 있음 → 배치모드 실행 불가를 명확히 알리고 종료 (에디터 강제 종료 금지).
- 디스크 공간 부족 → 실행 전 확인, 부족하면 실행기 오류로 구분.
- 리포트 이미지 합계가 아티팩트 한도를 넘음 → 썸네일 해상도·품질을 낮추고, 원본은 로컬 경로로 안내.
- 커밋되지 않은 변경이 있는 상태의 증거 → 리포트에 "작업 트리 변경 있음" 경고, 완료 판정 불가.

## 비기능 요구사항
- 결정론: 같은 커밋·같은 프로필에서 2회 실행한 스크린샷은 차이 0이어야 한다 (마스크 영역 제외). 아니면 그 시나리오는 불안정으로 표시하고 실패 처리.
- 재현성: 리포트만 보고 같은 실행을 다시 할 수 있게 실행 명령과 인자를 리포트에 남긴다.
- 격리: 검증 실행은 사용자 세이브·설정을 건드리지 않는다 (전용 데이터 폴더).
- 의존성: 맥 기본 + 설치된 Unity·Chrome·Python(Pillow, numpy)만 사용. 추가 설치가 필요하면 스크립트가 안내한다.

## 수용 기준
- AC-01 [로직]: 일부러 실패하는 테스트 1개와 통과 테스트 2개를 돌리면, 리포트 스크린샷 맨 위에 실패 1건이 메시지와 함께 보이고 판정은 실패다.
- AC-02 [로직]: 컴파일 에러가 있는 상태로 실행하면 판정은 실패이고 리포트에 `error CS` 줄이 보인다.
- AC-03 [E2E]: 샘플 화면(카드 3장 + 버튼 1개) 시나리오를 smoke 3 프로필로 돌리면 프로필별 캡처 3장이 나오고, 각 캡처의 해상도가 프로필 해상도와 같다.
- AC-04 [E2E]: 같은 커밋에서 같은 시나리오를 2회 돌리면 모든 캡처의 차이가 0이다.
- AC-05 [E2E]: 샘플 화면의 버튼 색을 바꾸면 해당 단계가 전 프로필에서 차이 실패로 표시되고 차이 이미지에 버튼 영역이 강조된다.
- AC-06 [E2E]: en 언어에서 일부러 넘치게 만든 라벨은 `잘림 없음` 단언으로 실패한다.
- AC-07 [E2E]: 렌더가 검은 화면이면 기준 이미지가 없어도 실패한다.
- AC-08 [E2E]: 기준 이미지가 없는 단계는 "기준 후보"로 표시되고, 승인 명령 후 재실행하면 통과로 바뀐다.
- AC-09 [성능]: 성능 구간에서 프로필별 p95 프레임 시간·GC·드로우콜·삼각형·메모리가 기록되고, 예산을 넘긴 값은 실패로 표시된다.
- AC-10 [성능]: 이전 측정보다 일부러 15% 느리게 만든 구간은 회귀 실패, 5% 느린 구간은 통과로 표시된다.
- AC-11 [결정론]: 같은 시드로 2회 실행한 샘플 시뮬의 해시가 같고, RNG 호출 하나를 일부러 추가하면 갈라진 첫 체크포인트가 보고된다.
- AC-12 [로직]: 플레이어 실행 중 경고 로그 1개가 나오면 판정은 실패이고 리포트 로그 요약에 그 줄이 보인다. 무시 목록에 사유와 함께 넣으면 통과하고 리포트에 무시 항목으로 보인다.
- AC-13 [E2E]: 한 프로필에서 플레이어가 크래시해도 나머지 프로필 결과는 정상으로 나오고, 크래시 프로필은 실패로 표시된다.
- AC-14 [E2E]: `report.html`이 400px 폭에서 가로 스크롤 없이 읽히고(격자·표·코드 블록 제외), 아티팩트로 발행되어 링크가 출력된다. 리포트 상단에 커밋 해시·브랜치·실행 시각이 보인다.
- AC-15 [성능]: smoke 매트릭스(3 프로필, 샘플 시나리오)가 빌드 캐시가 있을 때 5분 안에 끝난다.
- AC-16 [E2E]: 프로필 해상도를 바꿔도 결정론 체크포인트 해시가 같다.

## 검증 · 증거
- E2E 시나리오: `e2e/000-sample-cards`(카드 3장 + 버튼, AC-03~08·13·16), `e2e/000-report-mobile`(리포트 400px 확인, AC-14). 대상 프로필: smoke (AC-13은 crash 주입 프로필 추가).
- 이 스펙 자체가 증거 체계를 만든다. 완료 시점의 증거는 이 스펙의 샘플 시나리오로 만든 `evidence/report.html` 하나로, AC-01~16이 모두 연결돼 있어야 한다.
- 실행기 자체 회귀 테스트(비교 알고리즘, 프로필 파싱, 리포트 생성)는 Unity 없이 도는 스크립트 테스트로 둔다.
